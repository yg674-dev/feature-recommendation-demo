关键设计决策Key design decisions
  • 看板不解释原因。The dashboard does not explain causes. F1 只做排序和分流。把「为什么」放进看板会让它变成一个永远读不完的页面，也会让 Agent 的结论失去可追溯的证据上下文。 F1 only ranks and routes. Putting "why" on the dashboard turns it into a page nobody finishes reading, and strips the Agent's conclusions of the evidence context they need.
  • Agent 的每条结论都必须绑定证据。Every Agent conclusion binds to evidence. 诊断面板固定四段结构：结论 / 根因假设 / 证据 / 下一步。证据只能来自指标、trace 样本、数据源状态、策略消费四类，凑不出证据的假设不展示——宁可少给一条。 The diagnosis panel has a fixed four-part structure: summary, hypothesis, evidence, next actions. Evidence may only come from metrics, trace samples, data source status or strategy usage. A hypothesis that cannot be evidenced is not shown — better one fewer than one unfounded.
  • 根因假设给置信度而不是唯一答案。Hypotheses carry confidence, not a single verdict. 现实里根因经常是叠加的（本例就是枚举映射变更 + 数据源延迟）。强行输出唯一根因会诱导用户只修一半。 Real root causes stack — this case is an enum mapping change plus a source delay. Forcing a single answer nudges people into fixing only half of it.
  • 数据源相同是减分项而不是加分项。A shared data source subtracts, not adds. 这是替代排序里最反直觉的一条。普通检索场景下同源意味着口径一致，但在故障场景下同源意味着一起挂。 The most counter-intuitive rule in the ranking. In ordinary retrieval a shared source means a consistent definition; in a failure it means failing together.
  • 适配标签是五档而不是「相似度百分比」。Fit is five labels, not a similarity percentage. 百分比无法回答「能不能直接用」。五档标签每一档都直接对应一条 IDSP 交接规则，能被写进提案。 A percentage cannot answer "can I use this". Each of the five labels maps to one IDSP handoff rule and can be written into a proposal.
  • Agent 对 IDSP 只读和提案，不直接写。The Agent reads and proposes on IDSP; it never writes. 分成读 / 提案 / 人工确认后写三层。策略变更影响线上，这一层的信任成本远高于特征创建，所以宁可慢一步。 Split into read, propose, and human-confirmed write. Strategy changes hit production, and the trust cost here is far higher than for feature creation — worth one extra step.
  • 一对多枚举映射永远不自动决定。One-to-many enum mappings are never auto-resolved. 本例 001 → P01 + P02，合并规则涉及业务判断。Agent 可以把选项列全，但勾选的动作必须是人做的。 In this case 001 → P01 + P02; the merge rule is a business judgement. The Agent can enumerate the options, but a human ticks the box.
  • 复用 RAG 知识库的索引流程而不是另起一套。Reuse the RAG indexing flow rather than building a second one. 派生特征走 FEATURE_CREATED → INDEXED → AVAILABLE_FOR_IDSP，和知识库同一条 embedding 管道。否则会出现「有这个特征但 Agent 找不到」的分裂状态。 Derived features follow FEATURE_CREATED → INDEXED → AVAILABLE_FOR_IDSP on the same embedding pipeline as the knowledge library. Otherwise you get the split state where a feature exists but the Agent cannot find it.

尚未解决的问题Open questions
  • 健康分的计算口径还没定。四类指标如何加权、是否按地区分别计算，需要和数据侧对齐。 The health score formula is undecided — how the four metric categories are weighted, and whether it is computed per region, still needs alignment with the data side.
  • 影子测试的时长目前写死 3 天。是否应该按策略流量自动推算，还是让 owner 填，需要看 IDSP 侧的能力。 Shadow test duration is hard-coded at 3 days. Whether it should be derived from strategy traffic or entered by the owner depends on what IDSP can support.
  • Agent 提案被驳回后的学习闭环还没设计。驳回理由如果不回流，同样的候选下次还会排在第一。 There is no learning loop after a proposal is rejected. If the rejection reason does not flow back, the same candidate ranks first again next time.
  • 多个特征同时异常时的合并诊断（例如同一数据源导致 18 个特征一起挂）目前只在 F1 有入口，诊断面板还是单特征视角。 Joint diagnosis when many features fail together — one source taking down 18 features — has an entry point on F1 but the diagnosis panel is still single-feature.
